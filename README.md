# platform

Інфраструктура «Лад» для локальної розробки й демо-сервера: PostgreSQL, Kafka, Keycloak і шлюз Traefik у docker-compose.

## Що потрібно

Docker Desktop (з Docker Compose v2), `make` і `age` для зашифрованих копій баз (`brew install age` на Mac, `sudo apt install age` на ВМ).

## Швидкий старт

```bash
make env
make up
```

`make env` створює `.env` з `.env.example`, а якщо `.env` уже є — дописує лише змінні, яких бракує (наприклад, після `git pull`), не чіпаючи ваших значень. Запускайте його після кожного оновлення platform.

`make up` чекає, поки всі контейнери пройдуть healthcheck. Перевірити стан — `make ps`, список усіх команд — `make`.

## Що всередині

| Сервіс | Контейнер | Адреса з хоста | Адреса з контейнерів |
|---|---|---|---|
| PostgreSQL 16.15 | `lad-postgres` | `localhost:5432` | `postgres:5432` |
| Kafka 4.3.2 (KRaft, один вузол) | `lad-kafka` | `localhost:29092` | `kafka:9092` |
| Traefik v3.7.17 | `lad-traefik` | `http://localhost` | — |
| Keycloak 26.8.1 | `lad-keycloak` | `http://localhost/idp` (через шлюз) | `keycloak:8080/idp` |
| solver (профіль `solver`) | `lad-solver` | — | — (лише Kafka) |

PostgreSQL, Kafka і прямий порт Keycloak (8180, для адмін-консолі) слухають лише `127.0.0.1`: ззовні машини вони недоступні.

`db-init` — одноразовий контейнер, який при кожному `make up` створює ролі й бази й завершується. Зараз це Keycloak (`keycloak`) і три бази сервісів — `tenant`, `school`, `timetable`, кожна з ролями `<svc>_owner`, `<svc>_app`, `<svc>_relay`, `<svc>_maint` (паролі — `TENANT_*`, `SCHOOL_*`, `TIMETABLE_*_DB_PASSWORD` у `.env`). Робоча роль одного сервісу до бази іншого не під'єднується. Наступний сервіс додається одним рядком `service_database <svc>` у `db-init/init.sh` плюс чотири паролі в `.env.example` і `docker-compose.yml`.

Автостворення топіків у Kafka вимкнене. Топіки створює `kafka-init` — одноразовий контейнер, як `db-init`. Він бере список з маніфесту `contracts/topics.v1.json` (contracts v0.2.0): 6 топіків по 3 партиції зі строком зберігання 7 днів і до кожного `<топік>.dlq` на 14 днів. Повторний запуск нічого не перестворює, лише повертає строк зберігання до значення з маніфесту. Змінився маніфест у contracts — оновіть список у `kafka-init/init.sh`.

### Сервіси в контейнерах (профіль `apps`)

Для розробки сервіси запускаються на хості (`make dev` у їхніх репозиторіях), а `make up` піднімає лише інфраструктуру. Щоб підняти систему цілком, як на ВМ:

```bash
make up-apps   # збирає образи з ../frontend, ../tenant-service, ../school-service, ../timetable-service і піднімає все
make smoke     # шлюз → сервіси → Keycloak → PostgreSQL → Kafka: реєстрація закладу доходить до school
make down-apps # зупинити все, включно з контейнерами сервісів
```

Перед кожним сервісом окремий одноразовий контейнер `<svc>-migrate` застосовує міграції під роллю `<svc>_owner`; сервіс стартує лише після нього. `make up-apps` сам перемикає шлюз на контейнери (web — nginx зі статикою з репо frontend), `.env` для розробки на хості не змінюється. Порт `/internal/v1` school-service (3102) доступний лише в мережі compose. Коли образи з'являться в реєстрі — `WEB_IMAGE`, `TENANT_IMAGE`, `SCHOOL_IMAGE`, `TIMETABLE_IMAGE` у `.env`.

### solver

Kafka-воркер CP-SAT (`lad-solver`) вмикається профілем: `COMPOSE_PROFILES=solver` у `.env`, далі звичайний `make up`. Поки образу немає в реєстрі, compose збирає `lad-solver:local` з клону репо solver поруч (`SOLVER_SRC=../solver`). Коли образ з'явиться в GHCR — `SOLVER_IMAGE=ghcr.io/diploma-project-group-5/solver:<тег>`.

| Параметр | Значення | Чому |
|---|---|---|
| `cpus` | 1.5 | ВМ має 2 vCPU; ~0.5 CPU лишається API, Kafka і PostgreSQL |
| `SOLVER_NUM_WORKERS` | 2 | 2 потоки CP-SAT на 1.5 CPU дають найкращу якість за замірами |
| `mem_limit` | 768m | пік 222 МБ на закладі з 45 класів; CP-SAT обмежено 512 МБ |
| `stop_grace_period` | 30s | на SIGTERM solver публікує найкращий розв'язок і виходить з кодом 0 |
| `SOLVER_STALL_MIN_S` | 0 (вимкнено) | рання зупинка; ставити 8, коли timetable прийматиме `stop_reason: "no_improvement"` |

Портів у solver немає; стан — healthcheck образу за файлом-пульсом. Повний опис змінних — у README репо solver.

## Keycloak

Realm `lad` описано у файлі `keycloak/realm/lad-realm.json`. До демо 13.11 realm змінюється лише через цей файл (рішення 60). Keycloak імпортує файл тільки тоді, коли realm ще немає, тож після зміни файлу потрібен `make kc-reset`: він видаляє базу Keycloak і імпортує realm заново.

| Що | Значення |
|---|---|
| Ролі | `sysadmin`, `scheduler` |
| Група `schedulers` | дає роль `scheduler`; tenant-service створює укладача одразу в ній |
| Атрибут `school_id` | лише адмін бачить і змінює; користувач змінити не може (перевірено) |
| Клієнт `web` | публічний, вхід з PKCE (S256), без пароля напряму; `school_id` у токені |
| Клієнт `tenant-service` | секретний, сервісний акаунт з правами лише на користувачів |
| Користувачі | `sysadmin` і демо-укладач `demo` (`school_id` = `DEMO_SCHOOL_ID`); паролі з `.env` |
| Паролі | від 10 символів, не дорівнює логіну; після 5 невдалих спроб — тимчасове блокування до 15 хв |
| Токени | access-токен 15 хв, сесія 8 год |
| Мови | українська (за замовчуванням), англійська |

Головне в токені укладача:

```json
{
  "iss": "http://localhost/idp/realms/lad",
  "azp": "web",
  "realm_access": { "roles": ["scheduler"] },
  "school_id": "5d0b6a1e-7c3f-4b2a-9e41-0a1d2c3b4e5f"
}
```

### Перевірка JWT у сервісах

`iss` у токені — публічна адреса (`LAD_PUBLIC_URL`), а ключі сервіс у контейнері бере внутрішньою мережею. Тому в сервісі дві змінні:

| Змінна | Локально (сервіс на хості) | Сервіс у compose |
|---|---|---|
| `OIDC_ISSUER` | `http://localhost/idp/realms/lad` | `http://localhost/idp/realms/lad` (на ВМ — `https://<домен>/idp/realms/lad`) |
| `OIDC_JWKS_URL` | `http://localhost/idp/realms/lad/protocol/openid-connect/certs` | `http://keycloak:8080/idp/realms/lad/protocol/openid-connect/certs` |

Сервіс перевіряє підпис, `iss`, `exp`, `azp = web` і роль у `realm_access.roles`.

### Токен для перевірки свого API

```bash
make token                                  # демо-укладач
make token u=sysadmin p=<SYSADMIN_PASSWORD> # системний адмін
curl -H "Authorization: Bearer $(make -s token)" http://localhost/api/v1/school/...
```

### Адмін-консоль

Локально: `http://localhost:8180/idp/admin`, логін `admin`, пароль `KC_ADMIN_PASSWORD`. Через шлюз (`http://localhost/idp/admin`) консоль закрита навмисно. На ВМ — через SSH-тунель: `ssh -L 8180:127.0.0.1:8180 <ВМ>`, потім та сама адреса.


### Тема входу «Лад»

Сторінка входу, зміна тимчасового пароля й сторінки помилок мають вигляд прототипу: власна тема `keycloak/themes/lad` (шаблони FreeMarker, стилі з дизайн-токенами frontend, шрифт Onest локально). Поле — «Логін», бо пошту система не зберігає; скидання пароля — через адміністратора. Тема записана в realm (`"loginTheme": "lad"`) для чистих установок. У Keycloak, що вже працює, її вмикає `make kc-theme` без `make kc-reset` — користувачі лишаються. Після зміни файлів теми — `make restart s=keycloak`.

## Маршрути шлюзу

| Шлях | Куди | Примітка |
|---|---|---|
| `/` | web | |
| `/idp/…` | Keycloak | вхід і токени |
| `/idp/admin`, `/idp/realms/master`, `/idp/realms/lad/account` | — | 403 ззовні; адмін-консоль — через SSH-тунель |
| `/api/v1/tenant/…` | tenant-service | |
| `/api/v1/school/…` | school-service | |
| `/api/v1/timetable/…` | timetable-service | |
| `/api/v1/public/…` | timetable-service | 10 запитів/с з однієї IP, сплеск до 20, далі 429 у форматі problem+json (тіло — з контейнера gateway-errors) |
| `/internal…` | — | 404 від самого Traefik: внутрішні маршрути сервісів через шлюз недоступні, і застосунок web їх теж не віддає |

Маршрути описано в `traefik/dynamic/routes.yml`. Traefik перечитує файл сам, перезапуск не потрібен.

## Правила для авторів сервісів

Під час розробки сервіс запускається на хості (`npm run dev`), а шлюз веде на нього через `host.docker.internal`. Порти домовлені для всіх:

| Сервіс | Порт |
|---|---|
| web | 5173 |
| tenant-service | 3001 |
| school-service | 3002 |
| timetable-service | 3003 |

Шлюз **не зрізає** префікс: сервіс отримує запит повністю, наприклад `/api/v1/school/classes`, і маршрути в коді оголошуються разом з префіксом.

Внутрішні маршрути `/internal/v1/…` слухають на **окремому порту**, на який шлюз не веде. Інакше `GET /api/v1/school/internal/v1/…` через шлюз дійшов би до сервісу. На публічному порту сервіс повинен віддавати 404 на такі шляхи.

Коли сервіс переїде в контейнер compose, його адресу змінюють у `.env`, наприклад `TENANT_UPSTREAM=http://tenant-service:8080`.

## Сід демо-закладу

Демо-заклад «Ліцей № 17» описано у файлі `seed/demo-school.json`: профіль з місткістю укриття, дзвінки на 7 уроків, 30 класів (1–11), 20 предметів, 48 вчителів і навчальний план. Дані вигадані, персональних даних немає: підпис вчителя — назва предмета з номером («Математика-1»).

Масштаб узято за рекомендацією зі заміру солвера (коментар у картці #21): на 12 класах місткість майже нічого не обмежує, тому заклад має 30 класів і укриття ≈ 55 % від усіх людей у будівлі. Тоді частина класів у кожен день іде дистанційно, і на демо видно головне — вибір формату дня за місткістю.

Файл не пишеться вручну. Його збирає `node seed/build.mjs` з `seed/solver-problem.json` — виводу генератора solver (`lad-solver generate --classes 30 --shelter-ratio 0.55 --seed 0`). Ідентифікатори класів, предметів і вчителів — UUIDv5 від id генератора, тож чинна версія розкладу, яку solver порахує з того самого `solver-problem.json` (картка #72), збігається з даними сіду.

Розклад демо-закладу (картка #72) теж пораховано solver-ом з того самого `solver-problem.json`. Файли не перегенеровуються в CI, а id в них — id генератора, як у `solver-problem.json`:

| Файл | Що це | Вхід |
|---|---|---|
| `seed/timetable-main.json` | чинна версія `kind=main` (модель 1.1) | `seed/solver-problem.json` |
| `seed/timetable-alert.json` | шаблон тривог `kind=alert` (модель 1.2) | той самий генератор з `--kind alert`: відрізняється лише `kind` і `capacity` (`seats` 461 = `shelter_seats`) |

Обидва файли — результат `lad-solver solve` як є: `status`, `lessons`, `day_formats`, `conflicts`, `stats` і `provenance` (версії solver, моделі й OR-Tools, `input_sha256` канонічного JSON задачі, параметри). Команда:

```bash
lad-solver solve --in <problem.json> --out <result.json> \
  --time-limit 3000 --deterministic-time 120 --workers 2 --seed 0 --interleave
```

`--deterministic-time` разом з `--interleave` роблять результат відтворюваним: два прогони дають ті самі уроки й формати днів (настінний час у `stats` відрізняється). Поточні файли пораховано solver 0.3.0 (`model_version` `a+a2+b/2026-11-15`). Вони пройшли `lad-validate` (validator-lib 0.3.1, contracts 0.4.0) без конфліктів: у жодному немає класу без очних днів і жодного дня класу з «вікном» між уроками.

Завантаження — `make seed` після `make up-apps`:

```bash
make seed
```

Команда записує заклад `DEMO_SCHOOL_ID` з `.env` у реєстр tenant (укладач — користувач `demo` з realm), дані закладу в school, а в timetable — «Стан закладу» (дзвінки, субота, канікули, `snapshot_version`), QR-токени на кожен клас і вчителя та розклад від solver: чинну версію 1.1 з `seed/timetable-main.json`, опубліковану наказом з минулою датою (поля `publication` у `demo-school.json`), і шаблон тривог 1.2 з `seed/timetable-alert.json` на дзвінках тривог (`alert_bells`) з планом тривог у стані «чернетка». Наприкінці перевіряє, що все на місці. Перед завантаженням розкладу сід прибирає все, що лишилось від попереднього прогону демо: задачі, інші версії, активації й облік тривог, відсутності й заміни. `snapshot_version` однаковий у school і timetable. SQL друкує `seed/sql.mjs`; school і timetable пишуться робочими ролями `<svc>_app` з `set_config('app.school_id', …)`, тобто через ті самі політики RLS, що й сервіси (власник таблиць без політики рядків не бачить). Повторний `make seed` повертає дані закладу до файлу (класи, предмети й вчителі, яких у файлі немає, видаляються), а QR-токени лишаються ті самі, тож надруковані аркуші не застарівають.

Пріоритетні освітні галузі сід бере з того самого місця, що й timetable-service: зі змінної `PRIORITY_AREAS` у контейнері `lad-timetable-service`, а якщо її не задано — список за замовчуванням (математика, природничі науки, мова й література, громадянська освіта та історія). Тоді проєкція версії в сіді збігається з тією, яку будує сервіс. Якщо змінну задано порожньою або з невідомою галуззю, сід зупиняється ще до запису в бази: інакше timetable мовчки будував би розклад без пріоритетних предметів.

## Показ на своєму комп'ютері: `make demo`

```bash
make demo
```

Одна команда готує стенд до показу:

1. Зупиняє чужі контейнери, які тримають порти стенду (80, 5432, 29092, 8180), наприклад робочий PostgreSQL. Їхні дані не зникають.
2. Повністю зупиняє стенд і піднімає його заново разом із solver. Дані в томах лишаються, а мережа створюється наново: після простою стара мережа іноді заважає `db-init` знайти `postgres`.
3. Завантажує демо-заклад (`make seed`).

Якщо клон solver поруч на іншій версії, ніж `SOLVER_REF` у `.env`, команда попереджає, але сама клон не перемикає.

## Розгортання на ВМ

Демо для викладачів працює на одній хмарній ВМ: `docker compose` з тими самими сервісами, плюс HTTPS. HTTPS обов'язковий, а не «бажаний»: вхід через keycloak-js використовує PKCE, а Web Crypto, на якому він тримається, браузер дає лише на `https://` або `localhost`. На ВМ по http вхід не відкриється.

**Що потрібно.** Linux-ВМ з Docker і Compose, від 4 ГБ пам'яті (комфортно — 6 ГБ і більше), відкриті порти 80 і 443. Домен, що вказує на IP ВМ: безкоштовний піддомен DuckDNS або адреса `<ip-через-дефіси>.sslip.io`, для якої DNS-запис не потрібен. Поруч у одній папці — клони `platform`, `tenant-service`, `school-service`, `timetable-service`, `frontend` і `solver`.

**Перше розгортання.**

```bash
cd platform
make env      # створює .env з прикладу
# у .env: LAD_DOMAIN, ACME_EMAIL, LAD_PUBLIC_URL=https://<LAD_DOMAIN>,
#         COMPOSE_FILE=docker-compose.yml:docker-compose.vm.yml, COMPOSE_PROFILES=apps,solver,
#         свої паролі й секрети замість local-… (наприклад, openssl rand -hex 24)
make logrotate   # один раз, через sudo: журнал запитів шлюзу (IP) живе не довше 30 днів
make deploy SEED=1
```

`make deploy` спершу перевіряє `.env` і друкує всі проблеми одразу: домен, https-адресу, файли compose, профілі, паролі з прикладу, довжину секрету QR, публічний ключ age для копій (`BACKUP_AGE_RECIPIENT`, розділ «Резервні копії»), і що стоїть правило logrotate для журналу шлюзу. Потім оновлює клони сервісів, перемикає solver на тег `SOLVER_REF`, рендерить `traefik/traefik.vm.yml` для домену, збирає й піднімає стенд, а наприкінці запускає `make smoke`. Smoke перевіряє й те, що на ВМ легко пропустити: `/internal` через шлюз — 404, а відсутність вчителя демо-закладу доходить до solver і задача заміни завершується (`done` з solver 0.4.0, `failed / unsupported_job_type` з 0.3.0), а не висить у черзі до сторожа. Відсутність після перевірки видаляється. Сертифікат Let's Encrypt Traefik отримує сам при першому зверненні й зберігає в томі `traefik-acme`. На https-відповідях стоїть HSTS (рік, без піддоменів): після першого відвідування браузер сам ходить лише по https. `SEED=1` ще й завантажує демо-заклад.

**Журнал запитів шлюзу.** На ВМ Traefik пише журнал запитів з IP відвідувачів у `logs/traefik/access.log`, а не у вивід контейнера: вивід Docker обрізається лише за розміром, а IP за рішенням 05 зберігаються не довше 30 днів. Строк тримає системний logrotate ВМ: `make logrotate` один раз ставить правило `/etc/logrotate.d/lad-traefik` (щодня, 30 днів, стиснення; після повороту Traefik за сигналом USR1 відкриває новий файл), а `make deploy` без цього правила зупиняється. Локально журнал, як і раніше, у `make logs s=traefik`.

**Оновлення.** `git pull` у `platform`, потім `make deploy`. Сам `platform` скрипт не оновлює: bash читає скрипт по ходу виконання. Дані закладу `make deploy` без `SEED=1` не чіпає. Через `COMPOSE_FILE` і `COMPOSE_PROFILES` у `.env` решта команд на ВМ (`make logs`, `make restart`, `make seed`) теж працює з HTTPS-конфігурацією.

**Адмін-консоль Keycloak** на ВМ — лише через SSH-тунель: `ssh -L 8180:127.0.0.1:8180 <ВМ>`, далі http://localhost:8180/idp/admin.

**Пам'ять.** Кожен контейнер має `mem_limit`, а логи всіх контейнерів ротуються (3 файли по 10 МБ). Ліміти — це стеля, а не резерв: сума для довгоживучих контейнерів близько 4,4 ГБ, фактично стенд займає менше.

| Контейнер | Ліміт | Примітка |
|---|---|---|
| keycloak | 1 ГБ | heap — 60 % ліміту (`JAVA_OPTS_KC_HEAP`) |
| kafka | 1 ГБ | heap 512 МБ (`KAFKA_HEAP_OPTS`) |
| solver | 768 МБ | CP-SAT обмежено 512 МБ |
| postgres | 512 МБ | `shared_buffers=128MB`, `max_connections=100` |
| timetable-service | 384 МБ | |
| tenant-service, school-service | по 256 МБ | |
| traefik, web | 128 і 64 МБ | |
| gateway-errors | 32 МБ | тіла помилок шлюзу (429) у форматі problem+json |
| db-init, kafka-init, *-migrate | 128–512 МБ | одноразові, завершуються до старту сервісів |

## Резервні копії: `make backup`

`make backup` робить копії баз tenant, school, timetable і keycloak. Дамп знімає роль `backup`: вона лише читає (`pg_read_all_data`) і має `BYPASSRLS`, тож бачить рядки всіх закладів під FORCE RLS, але нічого не може змінити. Кожен дамп одразу шифрується утилітою [age](https://github.com/FiloSottile/age) публічним ключем із `BACKUP_AGE_RECIPIENT` і лягає в `BACKUP_DIR/<час UTC>/<база>.dump.age`. Копії, старші за `BACKUP_RETENTION_DAYS` днів (14), видаляються тим самим запуском.

Приватний ключ на ВМ не зберігається: втрата або злам ВМ не відкриває копій. Ключ створює той, хто відновлюватиме, на своєму комп'ютері:

```bash
age-keygen -o lad-backup.key        # приватний ключ — зберегти поза ВМ
# рядок «Public key: age1…» — у .env ВМ як BACKUP_AGE_RECIPIENT
```

Щоденний запуск на ВМ (cron користувача, о 02:30 за часом ВМ):

```bash
30 2 * * * cd /opt/lad/platform && make backup >> backups/backup.log 2>&1
```

Специфікація вимагає зберігати копії в Україні, тож каталог `BACKUP_DIR` треба синхронізувати в сховище в Україні (наприклад, `rclone sync`); вибір сховища — разом із вибором ВМ. Сам `make backup` пише лише локально.

Відновлення однієї бази (на стенді з тією самою схемою, приватний ключ — у того, хто відновлює):

```bash
age -d -i lad-backup.key backups/<час>/school.dump.age \
  | docker exec -i lad-postgres pg_restore -U postgres -d school --clean --if-exists
```

## Тести

```bash
make test
```

Піднімає окремий стенд `lad-test` (свої томи й мережа, порти назовні не відкриваються, робоче оточення `make up` не зачіпає), проганяє всі тести й прибирає стенд за собою. Перший запуск — до 2 хвилин, далі швидше. Якщо `make test` перервали, стенд прибирає `make test-down`.

| Файл | Що перевіряє |
|---|---|
| `tests/gateway.test.mjs` | маршрути шлюзу без зрізання префікса; адмінка Keycloak закрита разом з відомими обходами; ліміт `/api/v1/public`; заголовки безпеки; закодовані символи й заголовки-аліаси; `/internal` через шлюз — 404 |
| `tests/keycloak.test.mjs` | вхід і вміст токенів; перший вхід зі зміною пароля; незмінність `school_id`; блокування підбору; права сервісного акаунта tenant-service; адмін-консоль |
| `tests/realm.test.mjs` | статичні перевірки `lad-realm.json` і файлів теми входу, без запуску Keycloak |
| `tests/seed.test.mjs` | сід-файл збігається з виходом `seed/build.mjs`; масштаб і частка укриття; обмеження таблиць school-service; план без битих посилань, навантаження вчителя в межах ліміту; SQL сіду: лише свій заклад через `set_config`, екранування, перевірка вхідних змінних; `PRIORITY_AREAS` як у timetable-service. Сам `make seed` виконується на стенді `make up-apps` (як і `make smoke`) і перевіряє результат наприкінці |
| `tests/compose-check.mjs` | кожен контейнер з `mem_limit` і ротацією логів; сума лімітів у бюджеті; для ВМ — Traefik з HTTPS-конфігурацією, портами 80 і 443, томом сертифікатів і адресами контейнерів |
| `tests/deploy-check.sh` | `make deploy` не приймає `.env` без домену, з http-адресою чи паролями з прикладу й приймає правильно заповнений; шаблон Traefik для ВМ з тими самими захисними налаштуваннями; журнал шлюзу у файл, logrotate на 30 днів, `make deploy` без правила зупиняється |
| `tests/db-init.sh` | ідемпотентність `db-init`; ролі keycloak, tenant, school, timetable без зайвих прав і власники баз; межа між базами сервісів; `btree_gist` для timetable |
| `tests/kafka-init.sh` | ідемпотентність `kafka-init`; рівно 6 топіків з маніфесту + 6 `.dlq`; строки зберігання 7 і 14 днів, сегмент на добу; 3 партиції |
| `tests/backup.sh` | роль `backup` лише читає й бачить усі заклади під FORCE RLS; `make backup` робить 4 зашифровані копії, прибирає старі; копію видно лише після розшифрування приватним ключем; без ключа age — зрозуміла помилка |

Тести — JavaScript (`node --test`, без залежностей), запускаються в контейнері `node:24`, тож Node на машині не потрібен. Той самий `make test` запускає GitHub Actions на кожен пуш (`.github/workflows/test.yml`).

Правило: нова поведінка — новий тест у тій самій гілці; знайдена помилка — спершу тест, що її відтворює.

|---|---|
| `make up` | підняти все й дочекатися healthcheck (спершу дописує в `.env` нові змінні) |

| `make ps` | стан контейнерів |
